## 1. المبادئ المعمارية والتقنية الأساسية

1. **تطبيق الهاتف المحمول:**
   - يطوَّر كـ **تطبيق Flutter واحد فقط** يضم جميع أدوار المستخدمين.
   - يدعم التطبيق الأدوار التالية بشكل مخصص ومتكامل:
     - `STUDENT` (الطالب)
     - `DELEGATE` (المندوب)
     - `PRACTICAL_TEACHER` (الأستاذ العلمي/العملي)
     - `THEORETICAL_TEACHER` (الأستاذ النظري)

2. **لوحة العمادة والتحكم:**
   - تُبنى كلوحة ويب متكاملة باستخدام **Flutter Web**.

3. **الخادم المركزي:**
   - يطوَّر الخادم المركزي الموحد باستخدام إطار عمل **NestJS**.

4. **قاعدة البيانات المركزية:**
   - تدار وتُحفظ البيانات المركزية عبر قاعدة بيانات **PostgreSQL**.

5. **بروتوكولات الاتصال المركزي:**
   - تتم جميع الاتصالات والخدمات المتبادلة مع الخادم المركزي حصريًا عبر **REST API**.

6. **عزل الاتصال المباشر:**
   - **يُمنع منعًا باتًا** اتصال تطبيق الهاتف المحمول مباشرة بقاعدة البيانات المركزية PostgreSQL؛ وتمر جميع العمليات عبر REST API فقط.

7. **العمل دون إنترنت (Offline Capability):**
   - جلسة الحضور والتحضير يجب أن تعمل بشكل كامل ومستقل محليًا دون الحاجة لاتصال بالإنترنت أثناء تسجيل الحضور.

8. **الخادم المحلي أثناء الجلسة (Local Server):**
   - يعمل هاتف المندوب (`DELEGATE`) كـ **Local HTTP Server** محلي مؤقت لإدارة الجلسة.

9. **العملاء المحللون (Local Clients):**
   - تعمل هواتف الطلاب (`STUDENT`) كـ **Clients** تتصل بالخادم المحلي الخاص بالمندوب أثناء فترة التحضير.

## 2. قواعد وأحكام جلسة الحضور

10. **آليات التحضير:**
    - يدعم النظام التحضير باستخدام رمز الاستجابة السريعة Dynamic QR (`QR Session`).
    - يدعم النظام التحقق الحيوي (`Biometric Verification`).
    - يدعم النظام التحضير اليدوي (`Manual Attendance`).

11. **ديناميكية رمز QR:**
    - رمز الـ QR يكون ديناميكيًا ومستمر التغير، ومرتبطًا بجلسة حضور محددة وزمن صلاحية دقيق، ولا يجوز أن يكون رمزًا ثابتًا طوال الجلسة.

12. **معرف طلب الحضور الفريد:**
    - يتوجب تزويد كل طلب حضور متولد بـ **Request ID** فريد يضمن تتبعه والتحقق من صحته.

13. **منع التكرار الصارم:**
    - يُمنع منعًا باتًا تكرار تسجيل حضور الطالب داخل الجلسة الواحدة تحت أي ظرف.

14. **استمرارية وحفظ البيانات المحلية:**
    - تُحفظ جميع سجلات وطلبات الحضور في قاعدة البيانات المحلية داخل هاتف المندوب وتطبيق الطالب، وتبقى محفوظة بشكل آمن حتى نجاح عملية المزامنة الكاملة (`Synchronization`) مع الخادم المركزي.

15. **معالجة فشل التحقق الحيوي:**
    - فشل التحقق الحيوي للطالب لا يعني تسجيل غيابه تلقائيًا، بل يُحول إلى المسار البديل المحدد في بروتوكولات النظام.

16. **الأمان وحماية البيانات:**
    - تخضع جميع البيانات الحساسة والمعاملات المحلية والمركزية لقواعد مواصفة الأمان الحازمة المعتمدة في وثائق `Security Specification`.

## 3. حوكمة النظام والعقود البرمجية

17. **حظر التغيير الأحادية للعقود:**
    - لا يجوز تعديل عقد API المركزي (`api_contract`) دون موافقة كتابية صريحة من قائد المشروع.
    - لا يجوز تعديل هيكل قاعدة البيانات (`database`) دون موافقة كتابية صريحة من قائد المشروع.
    - لا يجوز تعديل بروتوكول الخادم المحلي (`local_protocol`) دون موافقة كتابية صريحة من قائد المشروع.
    - لا يجوز تعديل بروتوكول QR (`qr_protocol`) دون موافقة كتابية صريحة من قائد المشروع.

18. **التسميات الموحدة:**
    - يلتزم جميع أعضاء الفريق والوكلاء البرمجيين باستخدام الأسماء والمصطلحات الرسمية المعتمدة في المراجع والهيكل التنظيمي للمشروع.

19. **إمكانية الاختبار (Testability):**
    - يجب أن تكون كل وحدة برمجية أو مكون داخل النظام قابلاً للاختبار التلقائي والقياسي.

20. **نطاق التغييرات والدمج:**
    - كل تغيير أو إضافة برمجية يجب أن تكون محدودة النطاق، معزولة، ومصممة لتقبل الدمج المباشر والتكامل دون إحداث آثار جانبية.

21. **إدارة التعارضات:**
    - عند وجود أي تعارض في التوجيهات أو المواصفات بين أي ملفين، يتم التوقف فورًا والإبلاغ لاتخاذ القرار المعماري المناسب.

## 4. قواعد الوكيل البرمجي (AI Agent Rules)

تطبق القواعد التالية على كافة وكلاء الذكاء الاصطناعي والمساعدين البرمجيين العاملين في المشروع:

1. **قراءة الوثائق قبل التنفيذ:** قراءة وفهم كافة الوثائق المعمارية ودستور المشروع والعقود قبل البدء بكتابة أو تعديل أي جزء من النظام.
2. **عدم تعديل الملفات المشتركة دون تصريح:** يُمنع تعديل أي ملف في `shared/`, `api_contract/`, `local_protocol/`, `security/`, أو `database/` دون طلب وتصريح صريح من قائد المشروع.
3. **عدم تنفيذ مهمة خارج نطاق الطلب:** التقيّد التام بالنطاق المحدد في طلب قائد المشروع وعدم تجاوز الحدود أو تنفيذ افتراضات غير مطلوبة.
4. **عدم إنشاء مشروع بديل:** يُحظر إنشاء مشاريع جانبية، أطر عمل بديلة، أو إعادة هيكلة المجلدات المعتمدة.
5. **عدم تغيير المعمارية:** الالتزام الصارم بالتقنيات والمعمارية المحددة (Flutter, NestJS, PostgreSQL, Local HTTP Server) وعدم استبدالها أو إضافة تقنيات جديدة من تلقاء النفس.
6. **عدم تغيير أسماء الجداول أو الحقول دون موافقة:** الالتزام بأسماء الكيانات والحقول والـ DTOs والمخططات الرسمية دون تغيير.
7. **عدم اختراع API:** الالتزام التام بنقاط النهاية (Endpoints) وهياكل الطلب والاستجابة المعرفة في وثائق `api_contract`.
8. **عدم تغيير بروتوكولات النظام:** الالتزام ببروتوكولات الجلسة المحلية، التحقق الحيوي، الـ QR، والمزامنة المعرفة رسمياً.
9. **عند وجود تعارض: التوقف والإبلاغ:** في حال اكتشاف أي تناقض، غموض، أو تعارض في التعليمات أو بين الوثائق، يجب **التوقف فورًا** وإصدار تقرير بالتعارض لقائد المشروع وانتظار التوجيه.
